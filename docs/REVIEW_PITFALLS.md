# レビューで繰り返し出たピットフォール集

## この文書の目的と使い方

- コードレビューで繰り返し指摘された「型」を集めたもの。個別のバグ記録ではなく、次に同じ型の実装をするときの先回り集。
- 実装者（Antigravity）へは、Issue の brief で「この文書の T○ 節を前提にすること」と節番号で参照する。本文を brief に転記しない（正本はこの文書）。
- レビュアーへは、レビュー依頼で「繰り返しテーマ T○ の再発がないか」を観点に含める。
- 更新は裁定のたびに Muse が行う：新しい型が出たら節を追加し、既存の型に当たったら実例を 1 行足す。実例は最大 3 件までとし、古いものから落とす（肥大化防止）。

## T1 競合・順序・取りこぼし（最頻出）

型：非同期処理が並行して走ると、古い結果が新しい状態を上書きする／処理中に来たイベントを取りこぼす／タイマーや保留処理が移行後に残る。

実例：
- アバター配置の同期が一括更新中の中間状態を拾い表示が混在（legacy PR #163、2026-11-15）→ 世代トークンで最新結果のみ反映
- PngTuber のアバター連続切替で古い設定が後から上書き（公開 PR #10、2026-11-21）→ 切替ごとに世代番号
- 字幕連動の reconcile 実行中にミュート変化イベントを読み飛ばし、状態が食い違ったまま残る（private PR #19、2026-11-23）→ 適用後に再確認して追従

先回り策：
- 非同期の取得→反映には世代番号（または同等の無効化トークン）を付け、完了時に世代一致を確認してから反映する
- 長い一括処理の前後で「処理中に変化がなかったか」を再確認する経路を用意する
- 切断・移行のタイミングで、保留中のタイマー・古い世代の処理を必ず破棄する

## T2 状態の保全（消失・上書き・喪失）

型：守るべき既存状態を、空応答・古いスナップショット・エラー時の後処理で消してしまう。

実例：
- サーバー未登録（空）の応答でブラウザ側の既存配置が上書き消失（legacy PR #169、2026-11-15）
- config の read-modify-write の間に別経路の更新が割り込み、古い内容で書き戻して消失（private PR #7、2026-11-21、TOCTOU）
- 一時エラーを「対象なし」と同じ扱いにし、復帰用レコードを保存時に削除して喪失（private PR #19、2026-11-23）

先回り策：
- 「空・未登録・取得失敗」の応答で既存状態を上書きしない。空で保存して既存を消す経路を作らない
- read-modify-write は読み取りから書き戻しまでを同一のロック範囲に入れる
- エラー時にレコードを削除してよいのは「対象が恒久的に存在しない」ことが確定した場合だけにする（T6 とセット）

## T3 入力の境界

型：検証が想定ケースだけを通し、大小文字・空白のみ・型違い・重複が素通りする。読み取り側と書き込み側で検証の厳しさが食い違う。

実例：
- 予約名 "default" の大小文字違いが通過し、読み取り側で除外される参照不能データが書かれた（公開 PR #10、2026-11-21）
- 空白のみの channel 指定でフォールバックせず空チャンネルへ接続（legacy PR #190、2026-11-16）。空白のみの avatar は別 PR でも暗黙フォールバックになった（公開 PR #10）
- 設定値 `enabled` に文字列 "false" が入ると真として扱われた（private PR #19、2026-11-23）

先回り策：
- 名前・キー類は正規化（大小文字、トリム）した形で比較し、予約名チェックは既存チェックより前に置く
- 「キーが存在して、トリム後に空」は未指定と区別し、原則エラーにする
- 真偽値・数値など型のある設定値は型を検証してから使う（文字列の "false" を真にしない）。数値は範囲クランプもあわせて行う
- 新規作成時は重複チェックを先に行い、既存データを空値で上書きする経路を作らない

## T4 フォールバック・壊れたデータ・例外保護

型：フォールバックが副作用を持つ（本来のフォールバックを遮断する、暗黙に別対象へ倒れる）。保存データの破損で処理全体が落ちる。初期化処理が例外保護の外にあり、失敗するとスレッドや機能が死んだままになる。

実例：
- config 未存在時の書き込みが最小ファイルを作り、example へのフォールバックを遮断（private PR #7、2026-11-21）
- 状態ファイルに不正な UTF-8 行があると復元処理が例外で失敗（legacy PR #194、2026-11-16）
- ワーカーループの初期化呼び出しが例外保護の外にあり、失敗でスレッド終了（private PR #19、2026-11-23）

先回り策：
- フォールバック先を「作ってしまう」書き込みをしない。未存在時に書く場合は、その後の読み取り経路がどう変わるかまで brief に書く
- 保存データの読み取りは行単位・要素単位で壊れていても全体を落とさない（壊れた部分は捨てるか退避する）
- 「無効化に倒す」場合は無言にせず、理由をログ／標準エラーへ出す
- ループやスレッドの初期化も含めて例外保護の内側に入れ、失敗時はログ＋再試行待ちにする

## T5 再接続・切断・再起動の隙間

型：接続直後・切断直後・再起動直後の短い区間に、停止チェック漏れ・状態の不整合・再試行されない打ち切りが残る。

実例：
- 接続完了直後に停止要求を確認せず 1 回余分に処理が走る（private PR #19、2026-11-23）
- 再接続の移行過渡期に通知の重複処理とタイマー残留（legacy PR #193、2026-11-16）
- 切断時に古い同期世代を進め忘れ、再接続後に古い結果が反映される（legacy PR #169、2026-11-15）

先回り策：
- 接続・再接続の直後に停止要求と世代を確認する
- 再接続時は「前セッションの残り物」（タイマー、保留イベント、世代）を初期化してから始める
- 起動直後・再接続直後は外部側が未準備（NotReady 等）でありうることを前提に設計する（T6 とセット）

## T6 エラーの分類（一時 vs 恒久）

型：外部 API のエラーを一括りに扱い、一時的な失敗を恒久的な「対象なし・拒否」と同じ後処理（記録削除、打ち切り）にしてしまう。

実例：
- obs-websocket の code=207（NotReady）まで論理拒否として扱い、復帰記録の喪失と整合スキップが発生（private PR #19、2026-11-23）

先回り策：
- 外部 API のエラーは「再試行すべき一時エラー」と「対象が恒久的にないエラー」をコードで区別してから後処理を決める
- 一時エラーは状態を保持して再接続・再試行へ回す。打ち切る場合は次の再試行契機が存在することを確認する

## T7 テストの付け方

型：正常系は通るが、本番経路（デフォルト引数で定数を参照する経路など）と異常系がテストで踏まれていない。レビューでほぼ毎回「テスト補強」が付随する。

実例：
- 本番経路（default_base=None）がテストで踏まれていなかった（private PR #7、2026-11-21）
- 拒否されたアップロードで「ファイルが書かれていないこと」のアサーションがなかった（公開 PR #10、2026-11-21）
- import 時に起動しないことの分離検証がなかった（公開 PR #38、2026-11-23）

先回り策：
- デフォルト引数・本番定数を使う経路そのものをテストする（モックで定数を差し替えるケースを 1 件入れる）
- 拒否系は「エラーになること」だけでなく「副作用（ファイル作成、状態変更）が起きていないこと」までアサートする
- 今回の変更で直した指摘には、対応する回帰テストを同じ PR に含める

## T8 仕様・文書の整合

型：文書改訂で旧記述が残る／未確定の方針が確定扱いで書かれる／仕様と実装・文書同士が矛盾する。コードのレビューではなく文書のレビューで繰り返し出る。

実例：
- 仕様書の巻き戻し記載が旧仕様のまま残存（legacy PR #198、2026-11-16）
- README に旧環境（スペース運用）の記述が残存、バックアップ対象の記述が実装と未整合（household-finance PR #84、2026-11-16）
- 未確定の開始残高方針が仕様本文で確定扱いとなり、実装・他節と全面矛盾（household-finance の仕様改訂レビュー、2026-11-14〜16）

先回り策：
- 文書改訂では「変える箇所」だけでなく、同じ概念が出てくる全箇所（README、仕様書、設計書、改訂履歴）を検索してから直す
- 未確定事項は未確定と明記し、確定扱いの文体で書かない。確定日と決定者を添える
- 仕様と実装が食い違う場合は、どちらが正かを裁定で決めてから文書を直す（文書だけ寄せない）
